01

记录源码身份

第一条返回提交标识；第二条无输出才表示工作树干净。

若第二条列出文件，这次安装可能使用本地修改；先判断它们是否属于你要运行的版本。0.8.0 本身不能替代这一步。

02

建立隔离环境

以下以 macOS / zsh 为例；激活后，python 与 pip 应来自同一个 .venv。

python3 --version 必须是 3.11 或更高；仓库已经忽略 .venv/，但环境本身不属于科研数据或运行证据。

03

按用途安装当前 checkout

两种方式都读取当前目录；区别是后续源码修改是否立即影响环境。

科研使用 把当前源码构建并安装到这个环境

安装后，源码目录继续变化不会自动改变这个环境；要更新就从目标 checkout 重新安装。

开发维护 editable install，并增加 pytest

pip show 会增加 Editable project location，应指向目标 checkout。Python 源码修改会立即生效；若 pyproject.toml 中的版本、依赖或入口发生变化，仍需重新安装。

04

验收入口与导入

不要只在仓库根目录直接运行 import tpx；当前目录里的源码可能遮蔽已安装版本。先看发行包位置，再用隔离模式显示实际导入路径。

发行包存在
pip show 的 Name、Version、Location 可见；Location 应属于刚激活的环境。
三个 CLI 可执行
三个入口均返回 0.8.0；完整处理命令当前仍聚焦 tpdtpd。
SDK 可导入
-I 避免仓库根目录抢先参与导入；普通安装应显示环境内的 site-packages/tpx，editable 安装则应显示目标 checkout 的 tpx。
tpdtpd: command not found 怎么办？
  1. 确认已经激活刚才的 .venv，再运行 python -m pip show tpxtpxtpx。
  2. 运行 python -I -m tpxtpx.tpdtpd --version。成功只证明该 Python 能从安装环境导入模块，不能单独证明问题就是 PATH。
  3. 运行 command -v tpdtpd，确认脚本存在且来自当前 .venv/bin；缺失或仍指向旧环境时，使用同一个 python -m pip 重新安装，再执行 rehash。
!

安装成功，不等于科研结论成立

这些检查只证明发行包、命令入口与 SDK 导入可用；不证明原始数据兼容、参数选择正确、依赖环境完全一致或实验结论可靠。下一步仍从检查自己的文件开始。

数据沿路径前进，
判断留在研究者手里

每个处理阶段显式接收输入、写出可检查产物；程序不猜上一阶段，也不自动选择下一步。

准备

建立实验事实与人工确认的温程坐标。

  1. schema 4配置与原始数据检查
  2. suggest提出边界，等待复核
  3. fit / align显式边界与越界规则
校准

完整采集记录先完成相同的信号处理。

  1. vacuum查看当前电流映射后扣除本底
  2. fragmentation检查矩阵后求解物种电流
  3. calibration人工确认背景、平台与配气比
脱附

对齐后的 TPD 数据使用经复核校准。

  1. vacuum → fragmentation → [response_zeroing]按物种审核零点，apply 一次应用当前输入的全部匹配零点
  2. quantify → normalize显式运行四步定量；多 target 共用 long-format CSV
  3. integration baseline / peaks / areas → plot状态进 TOML，逐点证据进 records/，不生成分析 CSV

这是一条可审查的数据路径，不是自动 Pipeline、Recipe 或 DAG。

科研语义不打折

路径规则明确
输入来自命令参数或 TOML；表格处理省略 --output 时使用职责型固定文件名，下游不会扫描目录猜测上一步。
默认给人看
终端报告解释产物与参数；机器消费时显式增加 --json。查看两种输出模式。
来源随报告输出
完成报告列出已有输入、输出的路径与 SHA256、实际参数和 UTC 时间；长期留存需显式使用 --json 并保存标准输出。由阶段写入器管理的 CLI 产物在写入前拒绝输入碰撞和已有目标；这不能外推为整个 SDK 的全局保证。查看运行证据与边界。
缺失诊断可见
未匹配通道会在报告中明确列出，不让缺失悄悄消失。
